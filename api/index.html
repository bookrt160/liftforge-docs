    Blueprint API¶

    This page explains how the API fits together. The API reference lists the runtime and interaction classes. The AI classes are described in the NPC riding guide, and signage in Presets and visual sets.

    The 1.0 API is stable: names, parameter order and enum values do not change within 1.x; new members are added with defaults. Every item is a Blueprint node, event or property with a tooltip unless it is marked C++ only. A function's Blueprint name is its C++ name split into words (SelectFloor is Select Floor).

    1. The two entry points¶

    Everything that operates a car goes through two functions on ALFElevator. The generated buttons (ULFButtonComponent::PressButton), the operator console, the demo control panel and Blueprints all call them, and so does any network or AI layer you add. A network or AI layer therefore only has to sit in front of these two.

    Entry point Use
    ExecuteElevatorCommand(Command, FloorId, AccessLevel, OriginFloorId, BankOverride) Any ELFElevatorCommand: cabin call, hall call, destination call, doors, modes, faults, reset, resume, jog, inspection toggles. Returns true when a call was accepted or a service command ran. Raises OnCommandExecuted.
    CallToFloor(FloorId, OriginFloorId, AccessLevel) A trip for a passenger waiting at OriginFloorId who wants to go to FloorId on this car. The car is called to the origin and, when its doors are open there, the destination is selected. An empty origin is a cabin call.

    Routing rules of ExecuteElevatorCommand:

    • SelectFloor queues a cabin call on the car.
    • HallCallUp / HallCallDown go to the bank of the car (BankOverride, else GetDispatchBank()), which picks the car; with no bank the car queues the call itself.
    • DestinationCall goes to Bank->RequestDestination(OriginFloorId, FloorId); with no bank it is CallToFloor(FloorId, OriginFloorId) on this car.
    • EmergencyCall, Help and Phone have no built-in behaviour. They are accepted and raise OnCommandExecuted, which is how a project reacts to those buttons.
    • A bank-only panel (a button with a Bank and no Elevator) calls ALFElevatorBank::RequestHallCall / RequestDestination, the bank's own entry points.

    ELFElevatorCommand and the shared table:

    • ULFButtonComponent::Command is still an FName, because levels saved before the enum existed store it. The names never change (Select, Up, Down, Destination, Open, Close, Alarm, EmergencyCall, Help, Phone, Cutaway, Exploded, Labels, Overload, Obstruction, Normal, Independent, Maintenance, FireRecall, OutOfService, DoorJam, PowerLoss, EmergencyBrake, Stuck, Reset, Resume, JogUp, JogDown).
    • GetCommandType / SetCommandType convert between the name and the enum. A button whose name is not in the table logs one warning when pressed and does nothing, instead of failing silently.
    • C++ only (LFCommands.h, namespace LiftForge::Commands): Info(Command) returns FLFCommandInfo (button name, console caption, panel label, bIsCall); FromButtonName, ToButtonName, ServiceCommands() (the 21 service commands in console and panel order) and FloorCaption. The console and the panel both build from it. The old per-file tables and LFNames.h::Command are gone.

    2. Events and their order¶

    All events are multicast delegates on ALFElevator (the bank has OnAssigned and OnCallRejected). They fire on the game thread, from inside the call or tick that causes them.

    Event Parameters Fires
    OnDeparture Elevator, FloorId The car leaves a floor (FloorId is the floor it leaves).
    OnArrival Elevator, FloorId The car stops level at a floor, before the doors start to open. Also fires at a stop where the doors stay shut (fire recall stopover; the stop after Maintenance was entered while moving).
    OnStateChanged Elevator, State Every change of ELFElevatorState.
    OnDoorsOpening Elevator, FloorId The state becomes Opening.
    OnDoorsOpened Elevator, FloorId The state becomes Open (doors fully open).
    OnDoorsClosing Elevator, FloorId The state becomes Closing.
    OnDoorsClosed Elevator, FloorId The doors reach fully closed.
    OnDoorsChanged Elevator, bOpen Fully open (true) or fully closed (false). Kept from 0.x.
    OnModeChanged Elevator, Mode The operating mode changes.
    OnFaultChanged Elevator, Fault A fault starts or is reset (Fault None).
    OnCallRejected Elevator, FloorId, Reason A call is refused. Reasons: ELFCallRejectReason.
    OnOverloadChanged Elevator, bOverloaded The load crosses the capacity, either way.
    OnObstructionChanged Elevator, bObstructed The door light curtain (or the simulated flag) becomes blocked or free.
    OnPassengerEntered / OnPassengerExited Elevator, Passenger An actor that adds load (pawn, actor with ULFLoadComponent, simulating physics body) enters or leaves the cabin volume. An actor destroyed inside the cabin leaves without an exit event.
    OnCommandExecuted Elevator, Command, FloorId, bAccepted After ExecuteElevatorCommand ran (also for refused commands).

    Order guarantees, tested by LiftForge.API.EventOrder. Over one trip with the dwell time running out:

    OnDeparture, OnStateChanged(Accelerating ... Leveling), OnStateChanged(Idle), OnArrival, OnStateChanged(Opening), OnDoorsOpening, OnStateChanged(Open), OnDoorsOpened, OnDoorsChanged(true), OnStateChanged(Closing), OnDoorsClosing, OnStateChanged(Idle), OnDoorsChanged(false), OnDoorsClosed.

    So a door event always follows the matching state change, and when a handler runs the getters already show the new state. Change from 0.x: OnDoorsChanged(false) used to fire before the state became Idle; it now fires after, like the open case.

    An obstruction while the doors close gives OnObstructionChanged(true), OnStateChanged(Opening), OnDoorsOpening, ..., OnDoorsOpened (the doors reverse). A mode change raises OnModeChanged first, before any state change it causes.

    The light curtain is read while the doors are not fully closed, or whenever something is bound to OnObstructionChanged, so a parked car with closed doors and no listener does not query the overlaps.

    Call rejection reasons¶

    ELFCallRejectReason: UnknownFloor, SameFloor, InvalidDirection (no direction, Up at the top, Down at the bottom), AccessDenied, Fault, ResumeRequired (reset, waiting for Resume), OutOfService, Maintenance, FireRecall, IndependentService (hall call in Independent mode), InvalidConfiguration, NoElevatorAvailable (bank only). GetLastCallRejection returns the reason of the last call (None after an accepted call). A bank forwards the reason of the car it chose, or reports UnknownFloor / AccessDenied / NoElevatorAvailable / SameFloor itself through its own OnCallRejected(OriginFloorId, DestinationFloorId, Reason).

    3. Status getters¶

    IsMoving, GetTargetFloor (the floor of the trip in progress; None when not moving), GetTravelDirection (the committed direction, None when the car has nothing to do; it stays set while the doors are open), GetFloors, GetFloorIndex (-1 for an unknown floor), GetCurrentFloor, GetState, GetOperatingMode, GetFault, GetDoorFraction, GetCarElevation, GetCarVelocity, GetRequests, IsOverloaded, IsDoorObstructed, GetLoadKg, GetOccupants, CanServeFloor, EstimateArrivalSeconds, GetStatusText, GetLastCallRejection, GetDispatchBank, GetCabinFloor. GetConfigurationRef() is the C++ only const-reference accessor of the configuration.

    4. Move Elevator To Floor (latent Blueprint node)¶

    ULFMoveElevatorToFloorAction::MoveElevatorToFloor(WorldContext, Elevator, FloorId, OriginFloorId, AccessLevel, TimeoutSeconds), shown as Move Elevator To Floor with two exec outputs:

    • Arrived (Elevator, FloorId): the car is level with FloorId and its doors are fully open. With OriginFloorId the node counts only after the car has opened its doors at the origin.
    • Failed (Elevator, ELFMoveFailure, ELFCallRejectReason): CallRejected (reason set), Fault, ModeChanged (any mode other than Normal discards the queued calls), ElevatorDestroyed, TimedOut (TimeoutSeconds > 0), Cancelled (Cancel).

    Exactly one of the two fires, once. It completes at once if the car already stands open at the floor. In C++ call Activate() after creating it (Blueprints do this automatically).

    5. Banks, registration and validation¶

    • A car belongs to a bank when the bank lists it in Elevators, when the car names the bank in DispatchBank, when BankName matches, or after ALFElevatorBank::RegisterElevator.
    • Linking is two-way and automatic. At BeginPlay a car that names a bank calls RegisterElevator on it, and a bank calls it for every car it lists, so the car's DispatchBank is set and its hall buttons reach the bank. The authored Elevators array is never edited: registered cars are kept in a transient list and GetMembers returns the union.
    • RegisterElevator returns false (and logs) when the car already belongs to another bank or its BankName differs. UnregisterElevator removes the car and clears its DispatchBank. A call assigned to a car that leaves the bank is reassigned on the next bank tick.
    • ValidateBank(Errors): no cars, a car that belongs to another bank, a BankName conflict, two cars with the same ElevatorId, a car that shares no floor with the others. In the editor CheckForErrors reports the same in Map Check; at BeginPlay the bank logs one warning.
    • Calls assigned by the bank are re-evaluated on every bank tick (every 0.1 s): when the assigned car gets a fault, leaves Normal mode, leaves the bank, or is no longer a member, the call goes to the best remaining car, and waits unassigned if there is none.

    5b. Multiplayer¶

    No signature in sections 1 to 5 changed. What is new is how they behave on a network client, plus one component and a few getters.

    Server-authoritative cars. ALFElevator replicates (always relevant, no per-frame position). The server runs the state machine and writes a compact state (FLFElevatorNetState, internal): state, mode, fault, docked/target floor, the motion profile with its server start time, the door fraction and time of the last door change, lit calls (one bit per floor), load, light curtain, reset latch, the inspection views, and a small ring of the last 32 discrete events (state, mode, fault, arrival, departure, overload, obstruction, alarm) in the order the server raised them. A client rebuilds the motion and the doors from that state and the server clock (GetServerWorldTimeSeconds, smoothed so it never jumps), so a car moves smoothly between updates; a position jump after a late update (a fault stop arriving after a lost packet) is blended out over about 0.3 s. Also replicated: Preset, Configuration, bUseConfigurationOverride, ImportedParts, ElevatorId, BankName, DispatchBank, bShaftCollision, bStaticFixedParts (a change on the server rebuilds the car on every client, after the trip if it moves). The bank dispatches on the server only.

    On a client, every command is sent to the server. ExecuteElevatorCommand, CallToFloor, SelectFloor, RequestHallCall, RequestDoorOpen/Close, SetOperatingMode, InjectFault, ResetFault, ResumeOperation, MaintenanceJog, the Toggle* functions, ALFElevatorBank::RequestHallCall/RequestDestination and ULFButtonComponent::PressButton do not change the client's copy: they send the request through the local player's ULFElevatorInteractorComponent. Their return value on a client means "sent" (the bank functions return null there). The press animation and button sound play at once on the client. PlayAlarm and PlayButtonSound stay local sounds. Cars with bReplicates turned off keep the single-player behaviour on every machine.

    Events on clients. Every machine raises the elevator events for every car in the server's order (and so in the documented order of section 2): departure, the moving phases, arrival, door phases, mode, fault, overload, obstruction, and the alarm sound. The client replays the event ring, so several events that reach it in one update (the server sends at most its net rate) still come in the right order. When an update is lost, Unreal resends its properties later, so a newer update can arrive first: the client replays up to the missing entry and waits for the resend instead of skipping it. A client so far behind that the ring no longer reaches back takes the state as it is. OnPassengerEntered/Exited and GetOccupants stay local (each machine sees who stands in its cabin). Per-request events: the requesting client raises OnCommandExecuted and, when refused, OnCallRejected on its own copy when the server's answer comes back; a bank request raises OnAssigned or the bank's OnCallRejected on the requester's copy. Move Elevator To Floor works on clients too (a refusal arrives as an event). A client that joins late takes the current state as it is and raises only OnModeChanged, OnStateChanged and OnFaultChanged for values that differ from the defaults; nothing older is replayed.

    ULFElevatorInteractorComponent (Runtime, player-owned). The server adds one to every player controller once a networked world has LiftForge cars (ULFElevatorSettings::bAutoAddInteractor, default on), or add it yourself to your PlayerController or pawn. Server-side checks on every request: AccessLevel (the server uses the lower of this and the level the caller asked for, so a client can lower but never raise its level), bAllowServiceCommands (off by default: only calls, doors, alarm and the help buttons), MaxRequestDistance (to the car's and shaft's bounds; 0, the default, turns the check off), MaxRequestsPerSecond (flood guard, default 20) and the overridable CanRunRequest. Functions: ExecuteElevatorCommand, CallToFloor, RequestHallCall, RequestDestination, PressButton (use them directly for split-screen), FindLocalInteractor, FindOrAddInteractor, event OnRequestCompleted. Set AccessLevel in your game mode's Post Login, as ALFDemoGameMode does (level 9 and service commands for every demo player).

    Getters. ALFElevator::IsNetworkProxy and ALFElevatorBank::IsNetworkProxy (true on a client copy). On a client GetCurrentFloor ignores the short visual blend the client applies after a correction.

    Inspection views are shared. Cutaway, labels and exploded view go through the server and change for every player (the exploded view also puts the car into Maintenance, which only the server can do). Setting bCutaway, bShowPartLabels or ExplodedAmount directly on a client copy is a local override that lasts until the server changes that view.

    Server-side callers (AI). An AI controller or any server code calls CallToFloor, ExecuteElevatorCommand or ALFElevatorBank::RequestDestination on the server's actors directly, with its own access level, exactly as in single player; no interactor and no RPC are involved, and every client sees the result.

    Riding. Generated components that a pawn can stand on (cabin floor, sills, shaft walls) have the same name on the server and every client and are network-addressable, so CharacterMovement can send the cabin floor as its movement base. Custom characters: see Using your own character; the important one is bStayBasedInAir = true on the CharacterMovement component.
