    Multiplayer guide¶

    LiftForge cars are server-authoritative. The server runs the state machine, and every client shows the same car, doors, displays and sounds. This page covers setup, what clients can do, how riding works over a network, and what to check when something looks wrong.

    1. What is replicated¶

    • The car's state. The server writes a compact state: state, mode, fault, docked and target floor, the motion profile with its server start time, the door fraction and time of the last door change, lit calls, load, light curtain, the reset latch and the inspection views. The position is not sent every frame: clients rebuild the motion and the doors from that state and the server clock, so a car moves smoothly between updates.
    • Events, in the server's order. The server also sends a ring of its last 32 discrete events (state, mode, fault, arrival, departure, overload, obstruction, alarm). A client replays them in order, so even when several events arrive in one update, handlers see the documented order (see Blueprint API) and the sounds, chimes and announcements play on every client. After a lost packet a client waits for the resend instead of skipping an event.
    • Configuration. Preset, Configuration, bUseConfigurationOverride, ImportedParts, bShaftCollision, bStaticFixedParts, ElevatorId, BankName and DispatchBank replicate. A change on the server rebuilds the car on every client (after the trip, if the car is moving). A car spawned at runtime by the server therefore also exists on clients.
    • The bank. It replicates, so a bank spawned at runtime exists on clients, but it dispatches on the server only.

    A car replicates by default (bReplicates). A car with replication turned off keeps the single-player behaviour on every machine.

    2. Set up a multiplayer project¶

    1. Save the map before you test. A map that was never saved ("Untitled") cannot replicate level actors by name, so clients cannot find the cars. Save the level first, then use Play In Editor with several players.
    2. Nothing else is required on the elevator or the bank. There is no checkbox to tick: cars replicate and the server dispatches.
    3. Players need the interactor component. The server adds a LFElevatorInteractorComponent to every player controller once a networked world has LiftForge cars. This is the setting bAutoAddInteractor in the LiftForge settings, on by default. If you prefer, add the component to your PlayerController or pawn yourself and turn the setting off.
    4. Set each player's access level in your game mode's Post Login (see section 3). The demo game mode gives every player level 9 and allows service commands.
    5. For a custom character, apply the settings in Using your own character.

    The demo game mode of the example maps already does steps 3 and 4. A VR pawn works for single player and for the listen host; for multiplayer VR, use a Character-based pawn (section 4).

    3. Calling and operating cars from a client¶

    On a client, every command is sent to the server instead of changing the local copy. This covers Execute Elevator Command, Call To Floor, Select Floor, Request Hall Call, Request Door Open / Close, Set Operating Mode, Inject Fault, Reset Fault, Resume Operation, Maintenance Jog, the Toggle... functions, the bank's Request Hall Call and Request Destination, and Press Button. You use the same nodes as in single player.

    • Return values. On a client the return value of these functions means "sent", not "accepted". The bank functions return null there.
    • Answer events. The player who sent the request hears the answer on its own copy of the car: On Command Executed, or On Call Rejected when the server refused it. For a bank request, On Assigned or the bank's On Call Rejected. Move Elevator To Floor also works on clients; a refusal arrives as an event.
    • Instant feedback. The button press animation and sound play at once on the client. Play Alarm and Play Button Sound stay local sounds.

    The interactor component and access levels¶

    LFElevatorInteractorComponent lives on the player. It sends the request and the server decides, with these checks:

    Check Meaning
    AccessLevel The server uses the lower of this level and the level the caller asked for. A client can lower its level, never raise it.
    bAllowServiceCommands Off (the default): only calls, doors, the alarm and the help buttons are accepted.
    MaxRequestDistance How near the player must be to the car and its shaft. 0, the default, turns the distance check off.
    MaxRequestsPerSecond Flood guard, 20 by default.
    CanRunRequest An overridable function for your own rules.

    Service commands are off by default. A player can make calls, work the doors and press the alarm and help buttons. Modes, faults, reset, resume, jog, the inspection views and the simulated load and obstruction are refused until you set bAllowServiceCommands to true on that player's interactor. Turn it on only for players who may stop or fault a car. The demo game mode turns it on for every player.

    Set AccessLevel in your game mode's Post Login. The component also has Execute Elevator Command, Call To Floor, Request Hall Call, Request Destination and Press Button, which you can call directly (for example for split-screen), plus Find Local Interactor, Find Or Add Interactor and the event On Request Completed.

    4. Riding in multiplayer¶

    Characters ride as they do in single player: the cabin floor is their movement base. LiftForge gives the cabin floor and the sills the same name on the server and on every client and makes them network-addressable, so CharacterMovement can send them as the base. Your character needs a few settings, listed in Using your own character. The one that matters most is bStayBasedInAir = true on the CharacterMovement component.

    Tested results with a listen server and with a dedicated server, 2 clients each, 50 ms each way (100 ms round trip) and 1 % packet loss each way, on UE 5.6, 5.7 and 5.8:

    • The car's height on a client differed from the server's by at most 0.027 cm at the same server time in normal runs; one run of 15 measured 1.3 cm during a server frame hitch.
    • A rider standing in the car showed steady height above the floor and a largest frame-to-frame step of 0.010 cm. No fall-through: the lowest point after a jump landing was above the floor.
    • A jump inside a moving car reached the same height as in a still room.
    • Riding, crouching and walking in and out produced almost no corrections. Under packet loss, Unreal's character movement can correct a player's position: about 7 cm when jumping, and in rare cases up to about 50 cm when sprinting fast. This is engine behaviour; LiftForge does not change it. In the same test setup, a jump gave a correction of 6.5 to 6.7 cm (4 times in 90 runs), and sprinting at 6 m/s gave corrections of 8 to 54 cm (5 times in 140 runs).
    • A car moving at 5 m/s was tested with a jump at speed.

    These numbers come from the automated tests on the author's PC, with 2 clients in one editor process; your network will differ. Multiplayer has not been tested over a real network or by human players.

    5. Late joiners and relevancy¶

    • The car is always relevant: it exists on every client regardless of distance, and it sends no per-frame position, so tall shafts need no relevancy tuning.
    • A client that joins mid-trip takes the current state as it is: it sees the car where it is, moving, with the right displays and mode. It does not replay old events (no old chimes). It raises only the mode, state and fault events for values that differ from the defaults.
    • The first state is applied once the client's network clock is valid, so a late joiner does not see a jump.
    • A client that reconnects while a car travels was tested.

    6. Inspection views over the network¶

    Cutaway, part labels and the exploded view are shared: they go through the server and change for every player. On a client they are service commands, so that player needs bAllowServiceCommands (section 3). The exploded view also puts the car in Maintenance mode, which only the server can do. Setting the cutaway, labels or exploded amount directly on a client's copy is a local override that lasts until the server changes that view.

    7. Events and the data that stays local¶

    • Elevator events fire on clients too. Every machine raises the elevator events (departure, the moving phases, arrival, door phases, mode, fault, overload, obstruction, alarm) for every car, in the server's order. Logic that must run once, such as NPC and gameplay logic, scoring, spawning, must check Has Authority first, or it will run once per machine.
    • Stays local per machine: Occupants, On Passenger Entered / Exited (each machine sees who stands in its own cabin).
    • Per request: the requesting client raises On Command Executed and On Call Rejected on its own copy when the answer comes back.
    • Getters. Is Network Proxy (on the car and on the bank) is true on a client copy. On a client, Get Current Floor ignores the short visual blend the client applies after a correction.

    8. Test checklist¶

    Run these with Play > Advanced Settings > Multiplayer Options: first Play As Listen Server with 3 players, then Play As Client with 2 players (a dedicated server). Turn on Run Under One Process, and Network Emulation for everyone with a custom profile of 50 ms each way and 1 % packet loss. Save the map first. Tick everything in both rounds.

    • Hall call from a client: the car comes on every screen at the same time, and chimes play near the car on every client.
    • Cabin call from a rider: the button animates at once, the LED lights on every screen, the car leaves after the doors close.
    • Destination call at a console: the bank assigns a car and the status shows it.
    • A floor above the player's access level: the press animates, no LED lights, the car does not go.
    • Two clients call the same car at once: both calls are served.
    • Ride up and down, with two players watching each other: no shaking, no sinking, level arrival.
    • Jump while the car accelerates, cruises and brakes: you land on the floor, no snap back.
    • Crouch while riding. Sprint out as the doors open.
    • Fault while a car carries a rider: the car stops at the same height on every screen, the alarm sounds, the rider stays on the floor. Reset, then Resume.
    • Fire recall while a car travels away: it stops at the next floor with the doors shut, returns and opens.
    • Maintenance with a jog; out of service while moving.
    • Overload toggle; stand in the doorway; passenger alarm.
    • Cutaway, exploded view, labels from a client: every screen changes.
    • Join a new client mid-trip, during a fault, and during a fire recall.
    • A client disconnects while riding.
    • Logs: no LogLiftForge errors, no "has no LFElevatorInteractorComponent" warning, and no warnings about unresolved or unmapped elevator components.

    p.NetShowCorrections 1 in a client console shows every movement correction; there should be almost none. Under packet loss, expect a few (see section 9).

    Automation test under packet loss. LiftForge.Network.PIE.ListenServer runs with 1 % emulated packet loss. For the reason above it can fail about 1 run in 10. If it fails, run it once more before you report a bug. The failures are movement corrections of more than 5 cm, not a fault in the elevator.

    9. Known limits¶

    • Not tested over a real network or by human players (section 4).
    • Server and Client build targets were not compiled. The launcher engine cannot build them, so dedicated-server behaviour was tested in the editor only.
    • Server only for commands that change a car. Clients send requests; the server decides. A client cannot raise its own access level.
    • VR pawn. The demo VR pawn is single player and listen host only, and it has not been tested on a real VR headset; its VR switch needs authority. For multiplayer VR, use a Character-based pawn.
    • Occupants and passenger events are local per machine.
    • Never-saved maps cannot replicate level actors.
    • Remote crouch on a moving car under packet loss. The crouch flag of a character replicates apart from its movement. If the packet with the flag is lost, another player's character riding a moving car shows its new height with the old capsule until the resend: a pop of up to the crouch height difference (about 28 cm with the default capsule) for about one round trip. This is how Unreal replicates crouch for other players' characters, not LiftForge, and it corrects itself.
    • Movement corrections under packet loss. Under packet loss, Unreal's character movement can correct a player's position: about 7 cm when jumping, and in rare cases up to about 50 cm when sprinting fast. This is engine behaviour; LiftForge does not change it.
    • Corrections right after you teleport a player into or out of a car are expected.
    • Pawns without CharacterMovement ride through LFRiderComponent, which carries the pawn on each machine but does not replicate its movement.

    10. Troubleshooting¶

    I press a button on a client and nothing happens. Check that the world has cars when the player joined (the interactor is added by the server), that bAutoAddInteractor is on or you added the component, and the player's access level. The log warns when a player has no interactor component.

    Clients cannot name the car, or the car does not appear. You played in an unsaved map. Save the level and try again.

    Jitter or snapping on clients while riding. Check that the character has bStayBasedInAir on, that you did not move the car to a later tick group or drive it from a Timeline, and that you do not change MaxWalkSpeed on the server and the client independently (for sprint, use the usual custom move flag).

    Another player pops up and down by about 28 cm when crouching in a moving car. See the known limits: with packet loss, Unreal shows the new height before the capsule until the crouch flag is resent. It corrects itself after about one round trip.

    A client falls through the floor when jumping in a moving car. Turn on bStayBasedInAir on the CharacterMovement component. See Using your own character.

    My game logic runs several times when a door opens. The door events fire on every machine now. Check Has Authority before gameplay logic.

    An NPC rides on the server but I do not see it on a client. NPC riding runs on the server only. Clients see NPCs through normal Character replication. See the NPC riding guide.
